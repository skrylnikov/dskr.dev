## ADDED Requirements

### Requirement: Repository-local Anvil workflow

The repository MUST contain an OpenSpec root whose `openspec/config.yaml` selects `anvil` as the default schema, and MUST vendor the complete Anvil schema snapshot from `jikkujoyce/openspec-schemas` commit `73eea60c622712a5d952ec1aec62da4e349f8c33` under `openspec/schemas/anvil/`. The vendored directory MUST also contain the upstream MIT license as `LICENSE` and source URL plus commit provenance as `UPSTREAM.md`.

#### Scenario: Anvil resolves and validates

- **GIVEN** a clean checkout with project dependencies available
- **WHEN** a contributor runs `openspec schema which anvil` and `openspec schema validate anvil --json` from the repository root
- **THEN** OpenSpec resolves `anvil` from `openspec/schemas/anvil`, reports `valid: true`, and reports no validation issues

#### Scenario: Missing or invalid schema is rejected

- **GIVEN** the vendored Anvil directory is missing a required schema file or contains an invalid schema/template reference
- **WHEN** `openspec schema validate anvil --json` runs
- **THEN** the command exits non-zero or reports `valid: false`, so the checkout cannot be accepted as correctly initialized

#### Scenario: Vendored schema attribution is complete

- **GIVEN** the Anvil snapshot is present under `openspec/schemas/anvil/`
- **WHEN** the attribution check runs `test -s openspec/schemas/anvil/LICENSE`, searches that file for `Copyright (c) 2026 Jikku Joyce`, and searches `UPSTREAM.md` for the exact source URL and commit `73eea60c622712a5d952ec1aec62da4e349f8c33`
- **THEN** every command exits zero and the vendored copy is accepted as licensed and traceable

#### Scenario: Missing vendoring attribution is rejected

- **GIVEN** `LICENSE` or `UPSTREAM.md` is absent, empty, or does not contain the required copyright/source/commit value
- **WHEN** the same attribution check runs
- **THEN** at least one command exits non-zero and the vendored copy is not accepted

### Requirement: Anvil is the default for new changes

The project configuration MUST select `schema: anvil`, while still allowing a contributor to explicitly select another installed schema for an individual change.

#### Scenario: Default schema is selected

- **GIVEN** no `--schema` override is supplied
- **WHEN** a contributor creates a new change from the repository root
- **THEN** the new change metadata records `schema: anvil` and `openspec status --change <name> --json` reports `schemaName` as `anvil`

#### Scenario: Explicit schema override remains possible

- **GIVEN** another valid schema is installed
- **WHEN** a contributor creates a change with `--schema <other-schema>`
- **THEN** the change metadata records the explicitly requested schema without modifying the project default

#### Scenario: Invalid schema override is rejected

- **GIVEN** a contributor supplies a schema name that is not installed in the project
- **WHEN** they run `openspec new change <name> --schema <unknown-name> --json`
- **THEN** the command exits non-zero, reports a `change_error` status naming the available schemas, and creates no change directory

### Requirement: Codex integration

The repository MUST track the Codex integration generated by OpenSpec 1.11.0 for the `codex` tool target, including the target marker and all generated OpenSpec skills.

#### Scenario: Codex discovers OpenSpec skills

- **GIVEN** Codex starts at the repository root
- **WHEN** it discovers repository skills under `.agents/skills/`
- **THEN** the six generated `openspec-*` skills for propose, update, apply, explore, sync, and archive are present and `.agents/skills/.openspec-target` identifies `codex`

#### Scenario: Incomplete Codex generation is detected

- **GIVEN** the Codex target marker or any required generated skill is absent
- **WHEN** the tracked integration manifest is checked
- **THEN** the check fails and does not report the Codex integration as complete

### Requirement: OMP integration

The repository MUST track the OMP integration generated by OpenSpec 1.11.0 using OpenSpec's `oh-my-pi` tool target, including all generated OpenSpec skills and slash commands.

#### Scenario: OMP exposes OpenSpec workflows

- **GIVEN** OMP starts at the repository root
- **WHEN** it discovers `.omp/skills/` and `.omp/commands/`
- **THEN** the six generated `openspec-*` skills and six `opsx-*` commands for propose, update, apply, explore, sync, and archive are present

#### Scenario: Wrong OMP target is rejected

- **GIVEN** initialization uses an unsupported alias such as `omp` instead of `oh-my-pi`, or omits the OMP output directories
- **WHEN** initialization output and the tracked integration manifest are checked
- **THEN** the check fails and does not report the OMP integration as complete

### Requirement: Reproducible OpenSpec generation

The development image MUST install OpenSpec 1.11.0 explicitly, and the tracked integrations MUST be generated with that same version by `openspec init . --tools codex,opencode,oh-my-pi --no-animation`.

#### Scenario: Development image uses the expected generator

- **GIVEN** the development agent image is built from `dev/Dockerfile`
- **WHEN** `openspec --version` runs in the `dev-agent` container
- **THEN** it prints `1.11.0`

#### Scenario: Generator drift is detected

- **GIVEN** the installed OpenSpec version differs from 1.11.0 or regeneration changes tracked integration files
- **WHEN** the documented version and clean-diff checks run
- **THEN** at least one check fails and the generated files require explicit review before acceptance

### Requirement: Maintainer guidance

The development documentation MUST state the initialization command, the Anvil source repository and pinned commit, the validation commands, the generated integration paths, the refresh command, and that Anvil's content gates are agent-honored unless separate mechanical enforcement is added.

#### Scenario: Maintainer can reproduce and validate setup

- **GIVEN** a maintainer reads `dev/README.md`
- **WHEN** they follow the OpenSpec setup and validation section
- **THEN** `grep -Fq` checks against `dev/README.md` succeed for all of these literals: `openspec init . --tools codex,opencode,oh-my-pi --no-animation`, `https://github.com/jikkujoyce/openspec-schemas`, `73eea60c622712a5d952ec1aec62da4e349f8c33`, `openspec schema validate anvil --json`, `openspec validate --all --strict --json`, `openspec update .`, `.agents/skills`, `.opencode`, `.omp`, and `valid: true`

#### Scenario: Advisory gates are not misrepresented

- **GIVEN** no CI or git-hook gate has been added
- **WHEN** a maintainer reads the OpenSpec documentation
- **THEN** `grep -Fq 'Anvil review and TDD gates are agent-honored; OpenSpec validates artifact structure and dependencies, not verdict contents or execution order.' dev/README.md` exits zero, while `grep -Eiq 'OpenSpec( CLI)? (mechanically )?(enforces|blocks).*(REVISE|red-green-refactor|DECISION: FAIL)' dev/README.md` exits non-zero
